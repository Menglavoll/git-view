# 测试与验收计划

## 前端单元与组件测试

当前项目未强制引入新的组件测试框架，因此优先补充纯函数测试和手动 GUI 验收。

必须覆盖：

- Tag ref 合法性校验；
- 附注说明 1～2000 字符边界；
- 并发数 1、3、20 合法，0、21、小数、空值非法；
- 统一 Tag 初始化后单行覆盖；
- 混合轻量/附注 Tag；
- 目录选择、单项目移除和继续添加项目；
- 预检查失败时创建按钮禁用；
- 重试只包含失败项目并重新回到预检查。

## Rust Provider 单元测试

使用现有 Provider 测试风格和 mock HTTP 响应，至少覆盖：

- GitHub 分支 head 映射；
- GitLab 分支 head 映射；
- Gitee 分支 head 映射；
- Git ref、Tag object 和 ref 的请求构造；
- Tag 已存在、分支不存在、无权限、限流、非法 Tag 名称映射；
- 附注 Tag 不支持时返回 `AnnotatedTagUnsupported`；
- Gitee Header / Query 两种 Token 模式均不泄露 Token；
- 三平台错误响应正文脱敏。

## 后端批量执行测试

- 项目全部成功；
- 部分成功、部分失败；
- 预检查失败阻止执行；
- 已有 Tag 不覆盖；
- 任务按并发数执行，最大并发不超过 20；
- 取消只影响等待队列；
- 执行时 SHA 变化能同时返回预检查 SHA 和实际 SHA；
- 重试只执行原失败项目，且重新预检查；
- 项目数量超过 20 时仍可执行，20 是并发上限而非项目数上限；
- 操作日志包含批量摘要和项目明细。

## 手动 GUI 验收

前置：至少配置可写的 GitHub、GitLab、Gitee 账号，并准备有多个目录、分支和可创建 Tag 的远程项目。

### 场景 A：选择和编辑项目

1. 树形视图勾选一个命名空间目录。
2. 确认全部子项目被选中。
3. 取消一个项目，打开批量页面。
4. 清除筛选后添加另一个项目。
5. 移除一个项目，确认项目数量正确。

### 场景 B：分支和提交信息

1. 打开一个项目的分支下拉。
2. 确认惰性加载分支列表。
3. 输入关键字筛选分支。
4. 选择非默认分支。
5. 确认展示短 SHA 和提交描述首行。
6. 输入不存在的分支，确认无法提交。

### 场景 C：轻量和附注 Tag

1. 保持项目 A 为轻量 Tag。
2. 将项目 B 改为附注 Tag，填写多行说明。
3. 为全部项目应用统一 Tag 名称。
4. 单独修改项目 C 的 Tag 名称。
5. 确认不同项目可使用相同 Tag 名称。
6. 测试空说明、2001 字符说明和非法 Tag 名称。

### 场景 D：预检查和确认

1. 准备一个已有同名 Tag 的项目。
2. 执行预检查，确认该项目失败。
3. 确认存在失败项目时不能进入创建确认。
4. 移除失败项目后重新检查。
5. 确认摘要核对平台、账号、分支、Tag 类型、Tag 名称、说明和预检查 SHA。
6. 返回修改后确认必须重新预检查。

### 场景 E：执行、取消和重试

1. 设置并发为 3，执行多项目批量创建。
2. 确认进度和逐项目状态正确。
3. 中途取消，确认等待项目变为取消，已发送项目继续完成。
4. 制造权限或 Tag 冲突失败。
5. 确认成功项目保留，失败项目不影响其他项目。
6. 点击一键重试失败项目，确认重新读取分支和 SHA，并再次弹出确认窗口。
7. 设置并发为 20，确认不超过 20 个项目同时执行。

## 通过标准

- 规格中的 FR-001～FR-025 全部有实现和测试证据；
- 三个平台至少各完成一次轻量 Tag 创建验证；
- 三个平台对附注 Tag 的支持情况有明确验证结果；不支持时能按设计阻止创建；
- 无 Tag 覆盖行为；
- 失败隔离、取消、重试和日志脱敏通过验收；
- 所有质量门禁通过。
